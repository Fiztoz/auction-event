📊 Reporting Service

Microservice Architecture — Management Proposal

Prepared: June 2026 | Version 1.0

📋 Executive Summary

The Reporting Service is a new microservice that will aggregate data from all other services (Selling, Buying, Bidding, Settlement) and provide real-time dashboards for three user roles: Admin, Seller, and Buyer.

This service enables data-driven decision making by providing actionable insights into platform health, seller performance, buyer activity, and financial metrics.

💰 Business Value

📈 Platform Health Monitoring

Real-time visibility into total users, active auctions, revenue trends, and system performance. Identify issues before they impact customers.

🛒 Seller Performance Tracking

Help sellers understand their listing performance, revenue trends, and optimize their auction strategies. Increase seller retention and satisfaction.

💰 Financial Reporting

Automated daily/weekly/monthly revenue reports. Track GMV (Gross Merchandise Value), settlement status, and payment flows.

⚡ Operational Efficiency

Automated approval queues, settlement pipelines, and status tracking. Reduce manual work and response times.

🗄️ Database Strategy

We use a dual-database approach for reliability and performance:

Feature MariaDB ClickHouse Why
Raw Events Log ✓ Primary ✓ Copy MariaDB = backup, ClickHouse = fast queries
Platform Daily Metrics ~ Fallback ✓ Primary ClickHouse = fast aggregations
Approval Queue ✓ Only ✗ Needs instant status updates
Settlement Pipeline ✓ Only ✗ Needs instant status updates
Seller Stats ~ Fallback ✓ Primary ClickHouse = fast aggregations
Bid Activity ~ Fallback ✓ Primary ClickHouse = fast time-series
🔒 Safety Net: If ClickHouse fails or is removed, MariaDB handles everything. No data loss. No code changes needed. Just flip a switch.

Phase 1: Foundation (2-3 days)

Set up the core infrastructure for event ingestion and data storage.

  • Create MariaDB schema (all 7 tables)
  • Create ClickHouse schema (analytics tables)
  • Implement event consumer
  • Implement projection worker
  • Create basic API endpoints
  • Write unit tests
✅ Deliverable: Working event pipeline that stores data in both databases

Phase 2: Admin Dashboard (3-4 days)

Build the admin-facing dashboard for platform oversight.

  • Platform overview (users, auctions, revenue)
  • Approval queue (pending products)
  • Settlement pipeline (payments, shipping)
  • Active auctions list
  • Admin dashboard UI
  • Write integration tests
✅ Deliverable: Admin can monitor platform health and manage approvals

Phase 3: Analytics (2-3 days)

Integrate ClickHouse for fast analytics with automatic fallback.

  • ClickHouse client implementation
  • Fallback logic (ClickHouse → MariaDB)
  • Seller leaderboard
  • Bid activity analytics
  • Migration script (ClickHouse → MariaDB)
  • Write performance tests
✅ Deliverable: Fast analytics with automatic fallback if ClickHouse fails

Phase 4: Seller & Buyer Dashboards (3-4 days)

Build role-based dashboards for sellers and buyers.

  • Seller: My listings + revenue
  • Seller: Auction performance
  • Buyer: My bids + won items
  • Buyer: Spending analytics
  • Seller dashboard UI
  • Buyer dashboard UI
✅ Deliverable: All user roles have access to relevant data

Phase 5: Polish (2-3 days)

Add real-time updates and polish the user experience.

  • Near real-time polling (every 15 seconds)
  • Loading states and error handling
  • Responsive design (mobile-friendly)
  • Documentation
  • Performance testing
✅ Deliverable: Production-ready dashboards with real-time updates

⚠️ Risk Assessment

Low Risk

ClickHouse Removal

MariaDB is always the fallback. Migration script exists. No data loss.

Low Risk

Data Consistency

Dual-write pattern ensures data is always in MariaDB. Event sourcing provides audit trail.

Medium Risk

Event Bus Dependency

If event bus fails, reporting stops. Mitigation: Event store buffers events.

Medium Risk

Performance at Scale

ClickHouse handles scale well, but MariaDB may slow down with 500M+ rows. Mitigation: Data retention policy.
